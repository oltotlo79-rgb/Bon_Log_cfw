`Bon_Log_cfw` deploys to **fly.io** as app **`bon-log`**, region **`nrt`** (Tokyo). Only compute moves to fly; DB (Supabase), Storage (R2), Cache (Upstash), Stripe, Resend, Sentry stay external. The fly app points at the **same Supabase DB** as the existing Vercel production. See [[project-relationship]].

Status: **live on the custom domain https://www.bon-log.com** as of 2026-06-07 (cutover from bon-log.fly.dev done — `GET /api/health` 200, origin-checked POSTs pass for www, bad origins still 403). fly certs issued+active for both `www.bon-log.com` and apex `bon-log.com` (Let's Encrypt). Originally deployed/working at https://bon-log.fly.dev since 2026-06-05.

Config files:
- `fly.toml` — app=bon-log, primary_region=nrt, Dockerfile build, http_service on :3000 with `/api/health` check, `min_machines_running = 1`. `[build.args]` carries the public `NEXT_PUBLIC_*` + `R2_PUBLIC_URL` (inlined into client bundle at build time; values filled in).
- `Dockerfile` — multistage standalone; builder declares `ARG`/`ENV` for each `NEXT_PUBLIC_*`; `ENV NODE_OPTIONS=--max-old-space-size=4096` (next build OOMs at the ~2GB default). Runner runs `node server.js`.
- `.github/workflows/fly-deploy.yml` — **the deploy path**. Runs `flyctl deploy --local-only` on an amd64 ubuntu runner. Triggers on push to master + manual dispatch. Needs GitHub repo secret `FLY_API_TOKEN` (`fly tokens create deploy -a bon-log`).
- `.github/workflows/cron.yml` — replaces Vercel crons. Calls the 4 `/api/cron/*` endpoints on schedule with `Authorization: Bearer $CRON_SECRET` (GET). Needs GitHub repo secret `CRON_SECRET` + variable `APP_URL`.
- `scripts/fly-secrets-import.mjs` — parses `.env.local` with dotenv (handles BOM/comments/quotes/multiline like SUPABASE_CA_CERT) and `fly secrets set --stage`s everything. Use this, NOT `fly secrets import` (which chokes on those).

Hard-won gotchas (cost real time):
- **Do NOT build locally / with fly's depot builder.** Local Docker host is **ARM (Windows on ARM)** → amd64 build runs under qemu, takes hours, segfaults. fly's depot remote builder is amd64 but only ~3.5GB RAM → `next build` (webpack, large app) SIGKILLs/OOMs. The classic builder (`--depot=false`) hits a flyctl Windows bug: `failed to parse daemon host "npipe:////./pipe/docker_engine"`. **Solution: build on GitHub Actions amd64 runner via `flyctl deploy --local-only`.**
- **`AUTH_TRUST_HOST=true` is REQUIRED** as a fly secret. Auth.js v5 only auto-trusts the host on Vercel; without it, `/api/auth/session` 500s with "There was a problem with the server configuration". Code has no `trustHost` set (`lib/auth.ts` / `lib/auth.config.ts`).
- **Google OAuth uses a SEPARATE client for fly** ("BON-LOG2") so the Vercel production client (`791016622981-...`) stays untouched. `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are overridden in fly secrets. The fly client must have JS origin `https://bon-log.fly.dev` + redirect URI `https://bon-log.fly.dev/api/auth/callback/google`. The actual client_id sent is decodable from the Google `redirect_uri_mismatch` error URL (`&client_id=`).
- Build image-pattern strictness is gated on `VERCEL_ENV === 'production'` (`lib/config/image-remote-patterns.ts`), unset on fly → build won't fail without R2 vars.
- Migrations are NOT a fly `release_command` (runner image lacks prisma CLI). Run from local: `npx dotenv -e .env.local -- npx prisma migrate deploy`.
- `fly secrets set ...` after deploy restarts machines (no rebuild) — fine for runtime env like AUTH_TRUST_HOST.

Done: deploy (GitHub Actions), auth (AUTH_TRUST_HOST + Google BON-LOG2), cron (GitHub `CRON_SECRET` secret + `APP_URL` variable — verified the publish-scheduled job returns 200), Stripe webhook (separate fly endpoint + `STRIPE_WEBHOOK_SECRET` overridden). Billing: fly requires a credit card on the `personal` org (https://fly.io/dashboard/personal/billing).

**Pre-existing SW bug fixed here (NOT bonnsa-sns — port it there too):** registration hung on "登録中…" (and earlier 503s) because `public/sw.js` `networkOnlyWithOfflineFallback` fabricated a `503 "Offline"` for non-HTML GET fetch rejections. RSC navigation requests (`?_rsc=`, Accept: text/x-component) hit this and broke App Router `router.push` (post-`registerUser` navigation), so the form never left its loading state. **Reproduced identically on Vercel prod (www.bon-log.com)** — confirming it's a synced-code bug, not a fly regression. Root cause refined: the SW's own `fetch()` fails for public routes in ALL environments (reproduced on desktop + phone/mobile-network + Vercel) — NETWORK_ONLY paths (feed etc.) work because the SW skips them; public routes (`/`, `/register`, `/register/verify-email-sent`) get intercepted. Top-level navigations survive via the browser's direct-fetch fallback, but `router.push`'s RSC `fetch()` cannot recover when the SW respondWith fails → stuck "登録中…".
Fixes (commits 7ffec7a8 then 57bc2f81): (1) only offline-fallback for `text/html`, re-throw otherwise; (2) **exclude RSC requests from SW interception** (`RSC: 1` header / `text/x-component` / `?_rsc=`) so client navigation data goes straight to network; (3) removed missing `/favicon.ico` from PRECACHE_ASSETS (its 404 made `addAll` reject, so `offline.html` never cached). `CACHE_VERSION` v2→v4. After deploy, clients must Clear site data once. **bonnsa-sns still has all of this — port `public/sw.js` there too.**

Registration also hung because `RegisterForm.tsx`'s success path did `router.push(verify-email-sent)` + `router.refresh()`: even though the action POST returns 200 and the verify-email-sent RSC GET returns 200, the client router never commits the navigation (the `router.push`+`router.refresh` idiom is used all over the app but races here, likely with the action re-render / a hydration mismatch). Fix (commit 97013c22): use `window.location.assign(ROUTE_VERIFY_EMAIL_SENT)` (hard navigation — bulletproof against router/RSC/hydration state); updated its test to mock `window.location` (whole-object replace pattern like CookieConsent.test). **Confirmed working on fly 2026-06-05 (reached the "email sent" screen). Also bonnsa-sns.**

Also fixed (commit 1e429831): the original `git archive | tar -x` sync corrupted two binary files — `public/images/generated/landing-motion/hero-{dark,light}-desktop-01.webp` both became 121024 bytes; restored to match source. Lesson: verify binary files after a tar-based sync.

**Custom-domain cutover (2026-06-07, commit f31c8ff1):** flipped `NEXT_PUBLIC_APP_URL` in `fly.toml` fly.dev→`https://www.bon-log.com`, aligned defaults in `scripts/fly-secrets-import.mjs` + `.github/workflows/cron.yml`, and `fly secrets set --stage NEXTAUTH_URL=https://www.bon-log.com` (landed with the rebuild deploy v12, not a standalone restart). **Gotcha that bit us:** `proxy.ts` `getAllowedOrigins()` derives the CSRF allowlist from `getAppUrl()` = **build-time-baked `NEXT_PUBLIC_APP_URL`**, so the still-running old build (v11, baked fly.dev) returned `403 unauthorized origin` for every `www.bon-log.com` POST (Sentry `[SECURITY] Blocked request from unauthorized origin`, incl. `/monitoring` tunnel + Server Actions) until v12 rebuilt with the new URL. A domain change therefore REQUIRES a rebuild, not just a secret swap. Runtime `ALLOWED_ORIGINS` (comma-sep, non-public env read at runtime) is the faster mitigation but was not used (chose to wait for v12). Local `git push` is blocked by the husky pre-push hook on this ARM-Windows machine (Application Control policy blocks rollup's `win32-arm64` native .node) — use `git push --no-verify`; real lint/test/build run on CI anyway.

Google OAuth done 2026-06-07: BON-LOG2 client now has JS origins + redirect URIs for `www.bon-log.com` AND apex `bon-log.com` (kept `bon-log.fly.dev` too); Google login verified working on www.

**More fly-standalone render bugs surfaced by the migration (same class as the SW bug — synced code that worked on Vercel breaks on fly's `node server.js` standalone), fixed 2026-06-07:**
- **`/api/og` (commit e75840ee):** built the OG background URL with `new URL('/images/...', request.url)`. On fly, `request.url` is the internal bind `https://0.0.0.0:3000` (HOSTNAME=0.0.0.0/PORT=3000 in Dockerfile), so Satori's image fetch failed → `failed to pipe response`. Fix: read `public/images/generated/ui/og-default.png` from the filesystem and embed as a base64 `data:` URL (request.url-independent, memoized). Verified 200 image/png. **NOTE: bonnsa-sns is on Vercel where request.url is the real host, so it's NOT broken there — the fs-read fix is still strictly better, but not urgent to port.**
- **DynamicServerError on 36 master-data pages (commit 8ac1411c + test fix 8315cf49):** pages under `(main)` declared `export const revalidate=3600` + `generateStaticParams` (static/ISR), but `(main)/layout.tsx` AND `components/premium/PremiumProvider.tsx` (which wraps ALL children) both call `await auth()` (→ headers). So static generation threw `DynamicServerError` ("couldn't be rendered statically because it used headers"), surfacing as 500s (219×/2days). True static is impossible here without PPR (per-user shell wraps everything). Fix: removed `revalidate`+`generateStaticParams` from all 36 pages, added `export const dynamic = 'force-dynamic'` (data still cached via unstable_cache, SSR keeps SEO). Updated 7 test files that asserted the old `generateStaticParams`/`revalidate=3600`. All 36 pages verified 200 in prod.

**UI/behaviour fixes 2026-06-07 (all CI-green at 0063c237):** apex `bon-log.com`→`www` 308 redirect in `proxy.ts` (stops the apex `unauthorized origin/referer` Sentry warnings + SEO canonicalization); `public/sw.js` now only intercepts `request.mode==='navigate'` (CACHE_VERSION v4→v5) — intercepting RSC/`router.refresh()` turned fetch failures into FetchEvent network errors and hung client flows; `CommentThread` now clears `optimisticComments` when the `comments` prop changes (render-time reset, NOT useEffect — eslint `react-hooks/set-state-in-effect` forbids setState-in-effect) so the "送信中..." optimistic placeholder doesn't persist forever; `PostCardHeader` shows Delete for an owner's OWN repost (was gated `isOwner && !isRepost` so own-repost menu was empty — now `isOwner` always shows Delete with `postId`=the repost row id; edit/pin stay `!isRepost`).

**Test gotchas that cost real time here:**
- Several post tests MOCK `@/components/post/DeletePostButton` to render `<button data-testid="delete-post-button">` (`PostCardHeader.test.tsx`, `timeline-postcard-branches.test.tsx`), so they assert by `data-testid`. The REAL `DeletePostButton` (menu variant) has NO such testid — it renders `<button aria-label="投稿を削除"><span>削除する</span></button>`. Tests that DON'T mock it (`PostCard.extended.test.tsx`) must query `getByRole('button',{name:'投稿を削除'})`.
- Opening the post `...` menu inside a full `<PostCard>` (role="link" card): `fireEvent.click(post-menu-button)` did NOT open it, but `userEvent.click` on the MoreHorizontal button (detected via `svg.querySelectorAll('circle').length===3`) DID. Isolated `<PostCardHeader>` works with `fireEvent`.
- When changing a component's conditional rendering, grep ALL of `__tests__` for tests asserting the OLD behaviour (they may query by text/`queryByText(/削除/)`, aria, OR testid — a single grep pattern misses some). The repost-delete change needed updates in 3 test files found only via successive CI failures.
